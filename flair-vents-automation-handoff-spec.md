# Handoff Specification: `flair-vents-automation` (Revised)

## System Overview & Architecture Plan

Project name: `flair-vents-automation`. Repo already exists (cloned, currently just `README.md` and `LICENSE` — no scaffolding yet).

Build a local management engine and Web UI using Bun, TypeScript, React, Postgres, and Redis running on a local NAS to control motorized smart vents and thermostat setpoints via the Flair API only (see Integration Mode below).

Logging is a first-class architectural concern from the start, not an afterthought bolted on after core logic works. Every piece of domain logic below — state machine transitions, allocation ranking, pressure safeguard math, hardware reconciliation, sync — should be built with its structured logging instrumented alongside it, not retrofitted once the feature is "done." See Logging & Observability below for the concrete requirements; treat that section as binding for every phase, not as a separate late-stage task.

Testing is equally first-class, from the same first commit. Unit and functional tests (Vitest) are written alongside each piece of domain logic as it's implemented — not as a catch-up pass once the state machine "works." Untested logic controlling physical HVAC equipment isn't a corner worth cutting to move faster; it's exactly backwards, since it's the corner that costs the most to unwind later. See Testing & Safety Validation below; treat it as binding throughout, same as logging.

### System Integration & Reference App

- Reference Application: `tesla-powerwall-automation` is the strict reference implementation for infrastructure patterns — DB models, Redis queues, OAuth client flows, Bun server wiring, containerized deployment to the QNAP NAS via Container Station, CI/CD through the existing GitHub Actions runner and self-hosted Docker registry, Caddy reverse proxy exposure, and shipping logs to the existing Loki/Grafana stack — and for MUI styling/theme conventions, including its established theme layer (see Styling & Design Framework). This is not a new deployment/observability stack; it plugs into the one that already exists.
- Base entity schema: every persisted entity implements the same base schema being established in `tesla-powerwall-automation` — `id` (UUID), `creation_date`, `modified_date` — for consistency across both codebases' data models. This applies to every table in this app's schema: `air_handler`, `zone`, `schedule`, schedule `events`, manual override records, the Flair OAuth token record, and anything else added later. No entity-specific exceptions — this is a base you build on, not an opt-in. See Data Modeling Conventions below for what else, beyond this base, gets a dedicated column vs. folds into JSONB.
- Scope Strategy: Replicate structural patterns, directory layouts, and design tokens from the reference project. Focus implementation effort strictly on core domain logic, schedule resolution, priority/allocation logic, structured logging instrumentation, and Vitest test coverage, and MUI-based UI components — logging and tests are part of the core deliverable, not a separate pass.

### Data Modeling Conventions

Beyond the base entity schema (`id`, `creation_date`, `modified_date` — see above), tables in this app favor JSONB for configuration-like data over one dedicated column per field. The rule: a field gets its own column only if it's a true index field — a primary key, a foreign key used for joins, or a field genuinely queried/filtered/sorted/uniquely-constrained at the DB level. Everything else — settings, thresholds, flags, optional per-entity attributes, anything that's fundamentally "configuration" rather than a relational key — folds into a `config` JSONB column (or a purpose-specific JSONB column, where an entity has more than one logically distinct blob). The payoff: adding a new tunable later (another per-zone parameter, another system setting) is a JSONB shape change in application code, not a migration. If a JSONB field later turns out to need real query performance, Postgres expression/GIN indexes can be added directly on a JSONB path without pulling the field out into its own column — so this isn't a one-way door, just a default to start from.

Applying this to the entities already described in this spec — the clear-cut cases (true relational keys, no real judgment call) are decided below; everything else is deliberately left open, flagged for a case-by-case call against the test above during implementation planning, rather than pre-deciding every field's placement here:

- `zone`: `air_handler_id` (FK, constantly joined/filtered on) and `flair_room_id` (nullable, unique — the lookup key the "Sync Zones from Flair" matching logic depends on) are clearly dedicated columns; nothing about them is a judgment call. Everything else on the zone — `name`, `vent_hardware_type`, `has_temperature_sensor`, `has_occupancy_sensor`, `assumed_fixed_position`, `duct_cfm_rating`, `thermal_load_flags`, `idle_baseline_position`, `comfort_tolerance_f`, `sensor_calibration_offset_f`, `min_vent_position`, `max_vent_position` — is a candidate for `config` JSONB by default, but a few of these (`name` for sorting/search, `vent_hardware_type` for how often allocation/pressure-safeguard logic filters on it) are genuine judgment calls worth deciding at implementation time rather than here, weighing actual query patterns against a JSONB expression index as the alternative to a dedicated column.
- `air_handler`: `flair_structure_id` (nullable, unique — same reasoning as `flair_room_id`, once Phase 0 confirms how Flair models multi-air-handler structures) is a clear dedicated column. `name`, topology mode, and pressure-safeguard thresholds are open to a case-by-case call, same as above.
- `schedule`: no clear-cut relational fields beyond the base columns and `name`. `default_inactive` and `events` are strong JSONB candidates — `events` specifically as its own JSONB array column rather than folded into a generic `config` blob, since it's the schedule's primary content, not incidental settings, and evaluating it (wraparound windows, DST-aware timezone resolution, overlap tiebreaks) already happens in application code rather than as a SQL query — but confirm at implementation time rather than treating this as locked in.
- Manual override records: `zone_id` (FK — needed every control tick to find active overrides) and `expires_at` (`timestamptz` — needed to query "what's currently active" and to sweep expired ones) are clear dedicated columns; this is exactly the kind of field the base entity schema's own timestamps don't cover, since it's a business-meaningful expiry, not a metadata timestamp. The override's actual value, hold-duration selection, and audit detail are JSONB candidates, open to confirmation.
- Flair OAuth token record: the one deliberate exception, not a case-by-case item. This follows whatever dedicated-column pattern `tesla-powerwall-automation` already established for credential storage (see Integration Mode) rather than this JSONB convention — credentials are a security-sensitive category with their own existing precedent to match, not a place to introduce a second pattern for consistency's sake.
- Global/system-wide settings (proportional band width, modulation step size, max steps per tick, spike threshold/window, stale-sensor-reading threshold, Away Mode defaults, `min_step_delta`, and the global default `zone_priority_order`): no relational structure here at all, so this is a strong candidate for a single-row settings table with just the base entity columns plus one `config` JSONB blob — about as clear-cut as the JSONB side gets, though still worth a quick confirmation rather than assuming.

### Logging & Observability

Given this controls physical equipment, logging is a first-class requirement built in from the first commit — not something added once the state machine "works":

- Structured logging throughout (JSON, not plain text — this ships to Loki, which is built for label-based structured queries). Every control-tick decision should be traceable after the fact: state transitions, allocation ranking results (which zones competed, which won, why), pressure safeguard calculations and any clamping applied, vent commands issued vs. skipped (Step-Delta Suppressor), reconciliation outcomes, comfort tolerance exclusions, spike detection triggers/decay, manual override apply/expiry, Flair sync reconciliation events, and equipment fault / emergency fail-safe triggers.
- Secret redaction is non-negotiable given how extensive this logging is. OAuth access/refresh tokens (persisted in Postgres per Integration Mode, not files) — and any other credentials — must never appear in logs, including in raw request/response payload logging used for debugging. Redact at the logger level (a scrubbing middleware/formatter), not by trusting every call site to remember.
- Log levels matter for alerting downstream: routine control-tick activity at debug/info (high volume, expected); degraded vents, pressure-safeguard clamping, sync conflicts, and emergency fail-safe activation at warn/error, so they're cheap to alert on in Grafana without drowning in routine noise.
- Given real-world Flair/Ecobee sensor reporting latency (often multi-minute), log each sensor reading's own last-updated timestamp distinctly from the poll timestamp, once Phase 0 confirms it's available. Don't log an unchanged, stale duplicate reading as if it were fresh new information every tick — that's misleading noise in Grafana and inflates log volume without signal. Making staleness itself visible/queryable is useful for diagnosing whether sluggish-seeming zone control is a logic issue or an upstream data-freshness issue.
- Sensor disagreement diagnostic: if Flair's API ever exposes more than one distinguishable temperature value for the same zone (relevant only if a zone somehow has both its own Flair puck and a separately-visible Ecobee SmartSensor value — not the case in this house today, where every room has exactly one Ecobee SmartSensor and nothing else), log a warn-level event whenever those values diverge beyond a configurable threshold, and surface it in the UI. This app has only one sensor per room to work with, so the actual observed incident that motivated this — a room at a 72°F setpoint showing 73°F via Flair while the Ecobee app showed 71°F for the same single sensor, persisting far longer than any reasonable reporting interval — turned out to be a staleness problem (Flair's sync from Ecobee getting stuck for that room), not a multi-sensor disagreement. See the Stale Sensor Reading Safeguard (Safety & Equipment Safeguards) for how that specific, already-observed failure mode is handled. A comfort-tolerance band doesn't protect against either version of this problem — tolerance guards against overly strict targeting of a *correctly measured* temperature, not against the input measurement itself being wrong or frozen.
- Ship to the existing Loki instance using whatever pattern `tesla-powerwall-automation` already uses for log shipping — not a new pipeline.
- Grafana dashboard is a required deliverable, added to the existing Grafana instance, covering at minimum:
   - System state timeline (COOLING_CALL/HEATING_CALL/FAN_ONLY/IDLE) alongside equipment call source data.
   - Per-zone target vs. reported vent position over time, with degraded-vent periods highlighted.
   - Per-zone temperature vs. setpoint and comfort-tolerance band over time.
   - Pressure safeguard aggregate open-area over time, with the topology's safety floor/cap annotated as reference lines.
   - Spike detection events timeline, and manual override activity.
   - Sensor disagreement events per zone, if that diagnostic ends up possible per Phase 0 (see above) — otherwise noted as unavailable rather than silently omitted.
   - Per-zone time-since-last-sensor-update, tracked continuously as a leading indicator — not just the binary stale/not-stale state from the Stale Sensor Reading Safeguard (Safety & Equipment Safeguards), but the actual trend, so a reading drifting toward the staleness threshold is visible before it crosses it, rather than everyone finding out only once the hard cutoff and alert fire.
   - Service health: control-tick duration/latency, Flair API error/rate-limit rate — operational health of the app itself, not just HVAC domain data.
- Email alerting for safety-critical events (dashboard is pull, this is push): emergency fail-safe triggered, Flair OAuth refresh failure, extended Flair outage past threshold, a vent remaining degraded past a configurable duration, and a zone's sensor reading remaining stale past a configurable duration (see Stale Sensor Reading Safeguard) — this last one directly caused real discomfort during review (a room's vent staying open non-stop well after the room had overshot cold), so it belongs in the same push-alert tier as the others, not just a dashboard panel someone has to notice. Use whatever email-sending capability the reference app already has, or a standard SMTP/transactional provider if none exists yet — not a new dashboard-only paradigm for events that need immediate attention.

### Phase 0: Flair API Discovery (Required Before State Machine Implementation)

Before building the HVAC state machine, run a discovery pass against the live Flair API using real account credentials:

- Authenticate via OAuth2 and fetch full JSON:API payloads for `structures`, `rooms`, and `vents` resources.
- Confirm which fields are actually present and populated, specifically:
   - Real-time equipment call state (e.g., whether the system is actively heating/cooling right now) vs. just the configured mode (Heat/Cool/Auto/Off).
   - Any stage-level or variable-speed modulation data (compressor stage, blower %, if present).
   - Any equipment fault/diagnostic fields surfaced through Flair (vs. only available directly from Ecobee).
   - Confirm `set-point-temperature-c` write behavior on `structures` and per-room setpoint/hold behavior, given the account's current "Set Point Controller" setting (Thermostat vs. Flair App — this account uses Flair App as authoritative).
   - Whether Flair's `structures` resource reliably surfaces Ecobee-sourced Home/Away state (not just Flair's own manual Home/Away toggle) — this determines the source for Away Mode below.
   - Whether Flair's API exposes which Ecobee SmartSensor(s) are included in the currently-active comfort-setting sensor group — this is what Driving Setpoint Selection (below) depends on for the pushed setpoint to actually correspond to the right room's temperature. If it's not visible via API, this becomes a manual native-Ecobee-app configuration step the user has to keep in sync, not something this app can verify or set.
   - Exactly which sensor Flair's per-room temperature field is actually sourced from, and whether it's the same physical sensor the Ecobee app shows for that room. This surfaced as a real, non-hypothetical problem during review: with a room's setpoint at 72°F, Flair reported the room at 73°F (still above setpoint, so Flair keeps calling for more cooling) while the Ecobee app's sensor for the same room showed 71°F (already a degree below setpoint) — a 2°F gap large enough to flip the deviation's sign, not just its magnitude, causing the vent to stay wide open long after the room was already overshot cold. This is a different failure mode from sensor reporting latency (see below) — it isn't necessarily that Flair's number is old, it may be reading a different sensor (its own Flair puck, if one is separately paired to the room) than the Ecobee SmartSensor the person in the room is actually being cooled/heated relative to. If Flair exposes multiple distinguishable sensor values per room, this app should use whichever one matches the Ecobee-side reading driving actual comfort, not just whatever Flair's own aggregate/room-level field happens to return. Note this is a distinct dependency from the Ecobee comfort-setting sensor-group item above: that one is about which sensor *Ecobee* compares against to decide when to call; this one is about which sensor *Flair* reports to *this app* as the input to per-zone vent modulation — both are "wrong sensor" risks, but at different layers, and both need separate verification.
   - Whether each room/sensor telemetry field in the `rooms`/`vents` payload carries its own "last updated" timestamp, distinct from the API response time — this determines whether observed multi-minute reporting delay is a Flair-side caching/polling artifact (potentially improvable) or purely the physical sensor's own reporting cadence (not improvable via software, regardless of how often this app polls).
   - Whether Flair's API exposes any way to distinguish a genuinely fresh reading from a repeated stale cached value, since this materially affects both spike-detection accuracy and log signal quality (see notes under Dynamic Thermal Spike Detection and Logging & Observability).
   - Whether Flair's API offers any way to actively request/force a fresh read for a specific room, rather than only passively receiving whatever Flair's own sync from Ecobee last cached — relevant given the observed incident where a room's reading stayed stuck for well over 10 minutes (see Stale Sensor Reading Safeguard, Safety & Equipment Safeguards). If such a lever exists, this app should use it once a zone crosses the staleness threshold, instead of only alerting and waiting for Flair's own sync to recover on its own schedule.
   - Whether Flair models a multi-air-handler home (multiple independent air handlers/Ecobee thermostats under one roof) as a single shared `structures` resource, or as separate structures per air handler — needed before the second and third air handlers get their own smart vents and get synced in (see Multi-Air-Handler Architecture above). Not blocking for the initial build (only Upstairs has vents today), but worth confirming while already in the API so it isn't a surprise later.
- Document actual schema findings in the repo (e.g., `docs/flair-api-schema.md`) before the state machine consumes any of these fields.
- Contingency: working hypothesis is that Flair's API surfaces everything this system needs. If discovery reveals a gap (e.g., no real-time equipment call-state or stage-level data), stop and report the specific gap before proceeding — do not silently substitute a workaround (such as inferring call state from setpoint-vs-ambient deltas). This is a joint architectural decision, not an implementation detail to resolve unilaterally.
- Away Mode contingency (exception to the above): if Ecobee-sourced Away state is reliably available via Flair, use it. If not, this is a case where it's fine to proceed independently — implement Away Mode natively in this app (see Away Mode below), since this microservice already owns scheduling and manual overrides and a native toggle is a small addition, not a workaround.

### Hardware & Environmental Context

- HVAC System Selection: HVAC topology mode (Single-Stage, Two-Stage, or Variable-Speed / Inverter) is configured per air handler (see Multi-Air-Handler Architecture below) — a property of that specific piece of equipment, not a house-wide setting. The house has 3 identical Bosch Premium IDP heat pump systems with variable-speed ECM blowers, same wiring (bridged Y) on all 3. Only one air handler ("Upstairs") is in scope for active control right now — the other two have no Flair smart vents installed yet.
- Smart Vents: Flair Motorized Smart Vents (915 MHz radio, battery-operated, sleep cycle causing 30–90 second actuation latency).
- Topology assumption: each air handler serves N configurable zones off it. The house has 3 air handlers total; multi-air-handler support is modeled from the start even though only one is configured and exercised initially — see Multi-Air-Handler Architecture below.

### Multi-Air-Handler Architecture

The house has 3 identical Bosch Premium IDP heat pump systems — 3 separate physical air handlers, same equipment, same bridged-Y wiring — each with its own independent Ecobee thermostat. Only the Upstairs air handler currently has Flair smart vents and is in scope for active control; the other two aren't part of this effort yet. Multi-air-handler support is wanted eventually, and since retrofitting a single-air-handler assumption later would be expensive, `air_handler` is a first-class concept from day one — even though only Upstairs gets configured and exercised in the initial build. (Deliberately not called "system" as an entity name — that word is already used throughout this spec for HVAC equipment topology type, single-stage/two-stage/variable, which is a different axis entirely; each air handler has its own topology mode.)

- `air_handler` entity: `id`, `name` (e.g. "Upstairs"), HVAC topology mode (Single/Two-Stage/Variable — all 3 air handlers run the same Bosch IDP equipment, but the mode is kept per-air-handler for generality since ductwork could differ), its own pressure-safeguard thresholds, and a reference to whichever Ecobee thermostat/Flair structure serves it (exact mapping pending the Phase 0 addition below).
- Every zone belongs to exactly one `air_handler_id`, including manually-added zones — a manual zone must specify which air handler serves that space.
- The HVAC state machine (COOLING_CALL/HEATING_CALL/FAN_ONLY/IDLE) is evaluated independently per air handler, not as one global house-wide state — each air handler has its own Ecobee call running on its own timing.
- Topology-Aware Pressure Safeguard math is scoped per air handler — each air handler's ductwork is independent, so aggregate open-area/CFM calculations never mix zones across air handlers.
- Driving Setpoint Selection is scoped per air handler — each air handler needs its own driving zone, to push a setpoint to its own Ecobee thermostat. The global default `zone_priority_order` can still be one house-wide ordered list spanning zones from every air handler, since contention resolution and driving-zone selection only ever compare zones within the same air handler — cross-air-handler relative position in the list doesn't matter. `driving_zone_id`, though, is a single-value override and can't represent "one override per air handler" as originally specified — it becomes `driving_zone_overrides: { air_handler_id → zone_id }`, a per-air-handler-keyed map, following the same override-field convention established for `comfort_tolerance_overrides`.
- The control loop iterates per active air handler each tick, computing state/allocation/pressure-safeguard/driving-setpoint independently for each rather than as one house-wide computation. As more air handlers come online, the Flair API rate-limit budget per tick needs to account for all of them combined, not just one.
- Grafana panels and structured logs carry `air_handler_id` as a label from the start, so dashboards and log queries can already facet by air handler even though only one has data today.
- Sync/import: it isn't yet known whether Flair models a multi-air-handler home as one shared structure or as separate structures per air handler (see Phase 0 addition below), so "Sync Zones from Flair" needs an explicit air-handler-assignment step during import/retrofit review rather than assuming it can infer the air handler automatically. For now, imported zones default to the single configured Upstairs air handler.
- Away Mode is treated as one whole-house toggle/setpoint applying across all air handlers' zones, not per-air-handler, since occupancy is naturally a whole-house concept — this is an assumption, not something explicitly confirmed, so flag it if you actually want Away Mode to vary by air handler.

### Integration Mode

- Flair-only integration. No direct Ecobee API client, no Home Assistant dependency. Flair's existing Ecobee bridge (with Set Point Controller = "Flair App") is the sole source of thermostat read/write and equipment signal, pending Phase 0 discovery findings.
- Flair App State: Structure/rooms locked in Manual System Mode (or target rooms set to Inactive) to bypass Flair's native cloud auto-balancing.
- Single Source of Truth: This microservice is the primary authority writing `percent-open` values (0%–100%) via the Flair REST API (`api.flair.co`).
- Authentication: OAuth 2.0 (v2) with refresh tokens — Flair's suggested approach for persistent access. `flair-api-client-py` is a useful reference for the auth flow and endpoint usage (auth code exchange, refresh, request shapes) — it's Python, so it's documentation for the protocol, not a dependency for this Bun/TypeScript project. The Flair app's OAuth client ID/secret (app-level config, not per-account tokens) are supplied via a gitignored `.env` file. The per-account access/refresh tokens obtained through the OAuth flow are a different thing — those persist in Postgres per the Token persistence rule below, not in `.env`, since they're issued at runtime and need to survive restarts.
- Token persistence: DB, not a file. The Python reference client persists tokens to a local file by default — this project instead persists access/refresh tokens in Postgres, following the same credential storage pattern already established in `tesla-powerwall-automation`, not a new mechanism.
- OAuth token refresh failure: if Flair's refresh token becomes invalid (password change, revoked app access, expired grant), detect this explicitly on the first failed refresh — don't let it manifest as silent, unexplained command failures. Trigger a critical alert (see Logging & Observability) and surface a clear "re-authenticate with Flair" state in the UI.
- Extended Flair outage: if the Flair API is unreachable for longer than transient rate-limiting (not just a single failed request), back off retries rather than hammering the API — vents hold their last successfully commanded position during the outage, since that's the safest assumption. Alert loudly once the outage crosses a configurable duration threshold, distinct from routine transient-error handling.

### Configuration Responsibility: Flair vs. This App

Flair-to-room hardware pairing already exists today and shouldn't be duplicated or fought:

- Flair app remains the source of truth for hardware pairing — which physical smart vent belongs to which room, and which Ecobee SmartSensor is associated with which room. This microservice does not re-implement vent/sensor-to-room assignment; it imports it. If you need to move a vent to a different room or pair a new sensor, that still happens in the Flair app, same as today.
- This app is the source of truth for everything Flair doesn't model: thermal load flags, CFM ratings, priority order, comfort tolerance, idle baselines, schedules, and — critically — rooms Flair doesn't know about at all (manual-vent rooms, hallways, returns), since Flair's room list only includes rooms it has a device paired to.
- Sync mechanism: an explicit "Sync Zones from Flair" action pulls the current Flair `rooms` list and creates/updates local zone records linked via a `flair_room_id` reference. Imported zones default to `vent_hardware_type: flair_smart_vent` and inherit live temp/occupancy telemetry from Flair automatically — the user fills in only the extended fields (CFM, flags, tolerance, priority) that Flair has no concept of.
- Manually-added zones (no `flair_room_id`) are added directly in this app's UI for topology completeness — typically `manual_fixed_vent` or `no_vent` types. These get no live Flair telemetry by definition, since Flair never tracked them; only their static `assumed_fixed_position` feeds into the pressure safeguard's total capacity math (see above).
- Drift handling — retrofit (vent added to a previously manual/no-vent room): on sync, a Flair room not yet linked to any local zone is surfaced as "unmatched" for user review, with a suggested match against existing local zones by name. The user either links it to the existing manual zone — converting it in place from `manual_fixed_vent`/`no_vent` to `flair_smart_vent`, preserving that zone's name, schedule assignments, and position in the priority order rather than starting over — or creates a fresh zone if no match applies. This is a review-required step, not silent auto-apply, since the hardware-type change activates fields (CFM rating, priority ranking, comfort tolerance) that weren't previously meaningful for that zone.
- Drift handling — sensor added/removed: Flair also owns sensor-to-room pairing (Ecobee SmartSensor or puck), independent of vent status — a room can gain or lose a sensor without any vent change. This updates `has_temperature_sensor`/`has_occupancy_sensor` automatically on each sync (lower risk, doesn't invalidate other config), but is surfaced as a passive notification — since it silently unlocks or disables Dynamic Thermal Spike Detection and precise Comfort Tolerance for that zone, the user should at least see that it happened.
- Drift handling — vent/sensor removed: if a previously-controllable zone loses its paired vent or sensor in Flair, degrade it gracefully (drop it out of active allocation / dynamic behaviors, similar to a `manual_fixed_vent`/`no_vent` zone) and alert, rather than letting it silently fail hardware reconciliation.
- Extend Phase 0 discovery to also nail down exactly how Flair's `rooms` resource distinguishes rooms with vents vs. pucks-only vs. neither — that structure determines how reliably the sync/import logic can auto-detect `vent_hardware_type` on import versus needing the user to confirm it manually.

### Zone Configuration Model (Generic, Not Hardcoded)

Zones/vents are fully user-configurable — no fixed count or fixed thermal-load categories baked into the system. Each zone either wraps an imported Flair room (`flair_room_id` set) or is a manually-added local zone (`flair_room_id` null) per the Configuration Responsibility model above.

#### Vent & Sensor Hardware Type (per zone)

Not every room has a Flair smart vent — returns, hallways, rooms with a fixed manual register, or sensor-only rooms all need to be representable without contorting the model.

- `vent_hardware_type` (per zone): `flair_smart_vent` (default for imported Flair rooms — remotely controllable 0–100%) | `manual_fixed_vent` (a physical vent exists but isn't remotely controllable — always a manually-added local zone) | `no_vent` (no distinct vent for this zone — e.g., a return, hallway, or open area; always a manually-added local zone).
   - For `manual_fixed_vent`, the user records an `assumed_fixed_position` (e.g., "always left fully open," or a known manual setting) — since the system can't read or command it, this is a static input the user maintains, used only for pressure-safeguard capacity math.
- `has_temperature_sensor` / `has_occupancy_sensor` (per zone, independent of vent type): whether an Ecobee SmartSensor or Flair puck is present. A zone can be sensored without being controllable (e.g., a hallway with a sensor but no vent), or controllable without a dedicated sensor.
- Only `flair_smart_vent` zones participate in the ranked priority-allocation competition — that's the only hardware type the system can actually command. `manual_fixed_vent` and `no_vent` zones are excluded from active allocation entirely, but:
   - `manual_fixed_vent` zones still count toward the pressure safeguard's total system open-area/CFM calculation via their `assumed_fixed_position` — see the note under Safety & Equipment Safeguards, since a manual vent left mostly closed eats into the closure budget available to the smart vents.
   - If either type has a sensor present, its temperature/occupancy readings still feed general monitoring, diagnostics, and Dynamic Thermal Spike Detection alerts — surfaced informationally, even though no corrective vent action is possible for that specific zone.

All zone types are schedulable (see Scheduling Engine & Data Model) — `manual_fixed_vent` and `no_vent` zones get a resolved `cool_setpoint`/`heat_setpoint` from the active schedule/manual-override/away logic just like `flair_smart_vent` zones do, even though that resolved setpoint can't drive a vent command for them. This matters for two reasons: it lets a sensored manual/no-vent zone (e.g., a hallway with a puck) be evaluated against a real target rather than raw ambient temperature with no context, and it makes such a zone eligible to be selected as the driving zone (see Driving Setpoint Selection) if it's the best-placed sensor for representing whole-home comfort — not just an artifact of it happening to have a vent.

Comfort tolerance and satisfied/demanding classification apply to all zone types, but are gated on `has_temperature_sensor = true`, not on vent type. A zone with no sensor has no temperature reading to evaluate against a setpoint at all, regardless of vent hardware — it cannot be classified satisfied/demanding, cannot be a driving-zone candidate, and its resolved schedule setpoint stays inert until a sensor exists. This isn't a new mechanism: it's the existing "sensor added/removed" drift-handling rule (Configuration Responsibility) already doing its job — the moment a sensor is added to that zone via Flair sync, tolerance/spike-detection logic activates automatically for it. `idle_baseline_position` and the Step 1–3 vent-position math remain `flair_smart_vent`-only regardless of sensor presence, since there's no vent to command either way.

#### Per-zone configurable attributes

`duct_cfm_rating`, `thermal_load_flags`, `idle_baseline_position`, and `min_vent_position`/`max_vent_position` apply only to `flair_smart_vent` zones — they're about vent-position math, and there's no vent to compute a position for otherwise. `comfort_tolerance_f` and `sensor_calibration_offset_f` apply to any zone with `has_temperature_sensor = true`, regardless of vent type, since both are about the temperature reading itself, not the vent (see note above on comfort tolerance's sensor gating).

- `duct_cfm_rating`: optional rated airflow capacity for the zone's duct run, used for CFM-weighted pressure safeguard math when provided. Not required — exact CFM measurement is overkill for most setups. If unset, fall back to a reasonable default (e.g., a standard duct-diameter-implied CFM value) so the pressure safeguard still functions on a simplified equal-weighting basis until/unless the user chooses to refine it per zone.
- `thermal_load_flags`: optional behavioral tags for predictable, structural heat gain — `high_internal_heat_load` (sun-exposed rooms, kitchens — gain that's reliably present at certain times of day), `distant_high_duct_loss`, `standard`. Fluctuating heat sources (e.g., a gaming PC that's only occasionally under load) are deliberately not modeled as a static flag — see Dynamic Thermal Spike Detection below.
- Priority is not a numeric field on the zone — see Proportional Vent Position Control & Priority-Based Contention Resolution below for the ordered-list approach.
- `idle_baseline_position`: per-zone baseline open percentage used whenever no active heating/cooling call is driving priority allocation — covers both IDLE and FAN_ONLY states. Default 100% (fully open) if unset, but this is the field a user would tune down for zones close to the air handler to prevent them from dominating recirculated airflow at the expense of distant zones.
- `comfort_tolerance_f`: optional, per zone — acts as the default when no schedule event overrides it. Acceptable ± band (°F) around the zone's resolved setpoint before it's considered "not yet satisfied." If unset (and no schedule override applies), the zone behaves as it does today — tightly targeted, no leniency. See Comfort Tolerance below.
- `sensor_calibration_offset_f`: optional, per zone, signed °F, default 0. A static correction the user applies to that zone's sensor to account for known calibration drift or placement bias (e.g., a sensor that consistently reads a degree warm). Applied additively to the raw Flair-reported temperature at the point of ingestion — every downstream consumer (deviation calculation, comfort tolerance classification, spike detection, the driving-zone reading used in Ecobee setpoint push, UI display) uses this *calibrated* value, never the raw one. The raw, uncorrected value is still retained in logs alongside the calibrated one, specifically so a real sensor problem (like the stale/stuck-sync incident above) isn't masked by, or confused with, a calibration correction — these are different problems and need to stay visibly distinguishable. Deliberately a different concept from the `measured_offset` used in the Ecobee setpoint-push mechanism (Ecobee ↔ Bosch IDS Interface) — that one is a dynamic, continuously-recomputed delta between two sensors for a specific purpose (keeping the pushed setpoint honest); this one is a static, user-set calibration constant for one sensor. Config-time validation should reject implausibly large values (e.g., beyond a few degrees) as almost certainly a mistake rather than genuine calibration drift.
- `min_vent_position` / `max_vent_position`: optional, per zone, 0–100%, defaulting to the unrestricted 0–100 range if unset. Constrains the range this specific vent is ever commanded within — e.g., a high-flow vent close to the air handler limited to 0–50% so it can't dominate airflow, or a distant vent limited to 50–100% so it's never closed enough to starve that zone. Purely optional, and independent per vent — most vents will have no restriction at all. This clamps the vent's commanded position at every stage: `idle_baseline_position` must itself fall within the configured range (validated and rejected at save time if not, per Config-time validation below, rather than silently clamped), Step 1's desired proportional position is capped to the range, and Step 2's ramping never moves the target outside it. The Topology-Aware Pressure Safeguard and Step 3 contention resolution both naturally respect it too, since they operate on positions that are already range-clamped by this point — no special-case handling needed there. The Equipment Fault Emergency Fail-Safe is the one exception: forcing all vents to 100% open bypasses this range entirely, same as it bypasses ramping and manual overrides, since equipment protection overrides a comfort/distribution preference.

#### Behavioral rules driven by thermal_load_flags (static/structural)

- COOLING_CALL: zones flagged `high_internal_heat_load` or `distant_high_duct_loss` get a boost applied to their desired proportional position (same modifier mechanism as occupancy/spike — see Proportional Vent Position Control), compensating for extra heat gain or duct losses rather than snapping to a separate "priority" state. Satisfied zones still rest at idle baseline once within tolerance.
- HEATING_CALL: invert `high_internal_heat_load` zone behavior — choke those vents to 15%–25% (supplemental local heat covers them); direct primary airflow to perimeter/cooler zones.
- FAN_ONLY (Recirculation): vents move to their configured `idle_baseline_position` per zone — not a blanket force-open. Uniformly opening every vent to 100% lets air preferentially flow through low-resistance/close-to-handler zones, starving distant or high-duct-loss zones of actual circulated air. Per-zone baselines let the user compensate for that duct topology.
- IDLE: same — all vents to their configured `idle_baseline_position` (default 100% open, tunable per zone).

### Dynamic Thermal Spike Detection (fluctuating heat sources)

A static flag can't represent a heat source that's only sometimes running — e.g., an office with a high-wattage gaming rig that spikes room temperature for a few hours a day but sits idle otherwise, in a zone that's also far from the air handler. This needs real-time detection, independent of any static flag, applied to every zone:

- Sample each zone's ambient temperature at the control-tick interval (60s) and maintain a rolling buffer (e.g., last 10–15 minutes) — in Redis, given the existing infra — to compute a smoothed rate-of-rise, avoiding false triggers from single noisy readings. Given real-world Flair/Ecobee sensor reporting latency, the buffer cannot safely assume one genuinely-new sample per 60s tick — several consecutive ticks may just re-read the same stale cached value, followed by a jump when a fresh reading finally lands. Key the rolling buffer off each reading's own timestamp (once Phase 0 confirms it's available) and compute rate-of-rise against actual elapsed time between distinct readings, not assumed fixed tick spacing. Otherwise this risks two failure modes: diluting a real spike across mostly-duplicate flat samples (missed trigger), or misreading a delayed-then-caught-up reading as a much steeper rate-of-rise than what actually occurred (false trigger).
- Configurable spike threshold: e.g., °F risen per rolling window, tunable in System Parameter Configuration alongside the other safety parameters.
- On spike detection:
   - During `COOLING_CALL`: the spiking zone's desired proportional position gets a boost (per Step 1 of Proportional Vent Position Control) and it ranks ahead of the occupancy bucket in Step 3's contention resolution if pressure-capped. The vent still ramps toward that boosted position via Step 2's rate limiting — reacting quickly relative to a normal deviation, but not slamming open in a single tick.
   - During `HEATING_CALL`: the spiking zone is treated exactly like a `high_internal_heat_load` structural zone — throttled, since the detected rise indicates an active internal heat source is already covering it. Throttling ramps closed the same way, rather than snapping shut.
- Decay/cooldown: once the rate-of-rise falls back under threshold for a configurable stabilization period, the zone's boost is removed and its desired position reverts to the plain Step 1 calculation. Use hysteresis here (not an instant on/off) to avoid the spike flag flapping and fighting the ramp limiter.
- This applies regardless of a zone's static `thermal_load_flags` — a "standard" zone can spike, and a `high_internal_heat_load` zone's structural gain doesn't prevent it from also spiking further on top of that baseline.

### Comfort Tolerance (Leniency Bands)

Without this, every zone — even ones that don't need precision — competes equally hard for constrained airflow whenever it's even slightly off its exact setpoint, which steals capacity from zones that actually need to be held tightly (e.g., bedrooms at night).

- Opt-in per zone. `comfort_tolerance_f` is unset by default, meaning a zone behaves exactly as it does without this feature — tightly targeted. A user explicitly widens it only for zones where precision doesn't matter, leaving critical zones (like bedrooms) untouched.
- A zone with a configured tolerance whose current temperature is within that band around the resolved setpoint is treated as satisfied: it's routed to `idle_baseline_position` and does not enter the ranked priority competition below, regardless of where it sits in the priority order. A zone with no tolerance configured has no such exemption — it always competes for airflow whenever it's off setpoint at all.
- Example: bedrooms left with no tolerance set behave as before — precisely targeted. Other zones given a ±2°F tolerance around 73°F effectively express "72–74 is fine," so they stop pulling airflow the moment they're comfortable, freeing capacity for the bedrooms without needing the priority list to do all the work.
- Scope: this governs per-zone vent allocation only. It doesn't affect whether the HVAC equipment itself is calling for heat/cool — that's still Ecobee/Flair's own thermostat logic (per Phase 0 discovery).
- Schedule-overridable, not just a static zone default: a single global tolerance per zone doesn't capture "tight at night, loose during the day" for the same room. A schedule event may optionally override a zone's tolerance for the duration of that event (same override pattern as `zone_priority_order`); if no event override is active, the zone's own `comfort_tolerance_f` applies; if neither is set, the zone is precisely targeted. `comfort_tolerance_overrides` is a `zone_id → tolerance_f` map scoped to the event — not a "separate event per zone" pattern like setpoints — since it's an override field (independent divergence within a shared event), and override fields are always zone-keyed maps for maximum flexibility. This is distinct from `cool_setpoint`/`heat_setpoint`, which are the event's primary fields and follow the separate-event-per-room pattern instead, matching Flair's existing UI. Comfort tolerance applies to all zone types now that scheduling covers every zone, gated on sensor presence rather than vent type (see note under Zone Configuration Model).

### Proportional Vent Position Control & Priority-Based Contention Resolution

This is the core mechanism for achieving smooth, low-fluctuation temperatures — the whole point of having 0–100% modulating vents instead of binary on/off. Vent position is a continuous function of how far the zone actually is from setpoint, not a two-state switch between "max airflow" and "idle baseline." Priority ordering only matters when there isn't enough total airflow capacity to give every demanding zone what it wants — it is a contention-resolution tool, not the default way position gets decided.

#### Step 1: Desired Proportional Position (per zone, per tick)

For each zone currently outside its comfort tolerance (see Comfort Tolerance — zones within tolerance rest at `idle_baseline_position`, unchanged from before):

1. Compute `deviation` = the zone's current *calibrated* temperature (raw Flair reading plus `sensor_calibration_offset_f`, see Zone Configuration Model) vs. its resolved setpoint (`cool_setpoint` during `COOLING_CALL`, `heat_setpoint` during `HEATING_CALL`) — signed and outside the tolerance band already excluded.
2. Scale the vent position linearly between `idle_baseline_position` (at the tolerance boundary, deviation ≈ 0 beyond tolerance) and a configurable max position (default 100%) across a configurable proportional band width (system-wide parameter, default e.g. 3°F — the deviation magnitude at which a zone is treated as maximally demanding). Deviations beyond the band width clamp at max position. If the zone has its own `max_vent_position` narrower than this system-wide max, the zone's own limit wins — it's a per-vent hard ceiling, not just a starting default.
3. This produces continuous, smooth vent movement as a zone approaches its target — a zone 0.5°F off gets a modest opening, a zone 3°F+ off gets fully open, with everything in between actually in between. No snapping.
4. Occupancy boost, Dynamic Thermal Spike Detection, and `thermal_load_flags` (high_internal_heat_load / distant_high_duct_loss during COOLING_CALL) all modify the desired position directly (e.g., a configurable percentage boost added to the computed position, or an effectively steeper proportional band for that zone) rather than jumping the zone into a separate priority bucket — this preserves continuity while still giving those zones a real edge when it matters.

#### Step 2: Modulation Steps & Ramp Rate Limiting

The "desired proportional position" from Step 1 is a target, not something commanded directly and instantly — jumping straight to it in one tick is exactly the "quick push of a large amount of air" this design is meant to avoid, matching how your variable-speed system itself favors steady, continuous airflow over abrupt bursts:

- Modulation step size: the continuous Step 1 calculation is quantized to a configurable step granularity (system-wide parameter, default e.g. 10%) — consistent, discrete increments rather than arbitrary fractional values, giving predictable, legible position values in the UI and logs.
- Ramp rate limiting: rather than commanding the target directly to the newly computed desired position, the commanded target moves toward it by at most a configurable number of modulation steps per control tick (e.g., 1 step per tick, tunable via `max_steps_per_tick`). A sudden spike-detection event still ramps the vent open gradually over several ticks rather than slamming it open in one shot — reacting appropriately, not erratically — while still reliably reaching full response within a bounded, predictable time.
- Relationship to the Step-Delta Suppressor (Safety & Equipment Safeguards, above): these operate at different layers and both apply. Ramp rate limiting decides how far the commanded target moves each tick (smoothness of intent, addressing fluctuation). The Step-Delta Suppressor then decides whether that tick's resulting change vs. the actual reported hardware position is large enough to bother dispatching a command at all (dispatch efficiency, gear/battery wear). The original spec's `Min Step Delta` concept was this second thing — this ramp limiter is the piece that was missing for actual smoothness.
- Emergency Fail-Safe is exempt from ramping — the force-all-vents-100%-open equipment protection response bypasses it entirely, since equipment protection takes priority over smoothness.

#### Step 3: Contention Resolution (only when total desired capacity exceeds the pressure safeguard)

In an adequately-sized system, most control ticks won't hit this path at all — each zone just modulates independently based on its own deviation. This only activates when the CFM-weighted (or equal-weighted, per the pressure safeguard's fallback) sum of all demanding zones' desired positions would violate the topology's closure cap:

- Global default zone order: one drag-and-drop reorderable list covering all zones, configured in System Parameter Configuration. Position in the list = priority (top wins first) when contention actually occurs.
- Schedule-level order override: a schedule event may optionally define its own drag-and-drop zone order, active only during that event's time window (e.g., a "Night" schedule's list puts bedrooms at the top; a "Day" schedule's list puts the office at the top). Zones not included in an active override list fall back to their position in the global default list, appended after the overridden zones.
- Resolution algorithm:
   1. Rank demanding zones using the active schedule/global order, partitioned by actively spiking → occupied → unoccupied (occupancy/spike still act as tie-break ranking here, in addition to modifying desired position in Step 1).
   2. Starting from the lowest-priority zone, reduce desired positions — first toward each zone's own `idle_baseline_position` floor — until the aggregate satisfies the pressure safeguard, preserving higher-priority zones' desired proportional positions as fully as possible.
   3. If reducing every zone to its idle baseline still isn't sufficient (rare, likely a misconfiguration), that's a signal worth surfacing as a warning rather than silently over-closing below the topology's hard floor.
- Because list order is inherently total, there's no numeric tiebreak to define beyond the bucket partitioning above.

This keeps the mental model simple day-to-day (drag bedrooms to the top for night, drag the office to the top for day) while making sure it's actually a fallback for genuine scarcity — not the mechanism deciding every zone's position on every tick.

### Core Operational Logic & State Machine

#### HVAC State Adaptation Tree

- State 1: COOLING_CALL — each zone outside comfort tolerance modulates continuously per its desired proportional position (see Proportional Vent Position Control above); priority ordering only intervenes under genuine pressure-cap contention. Satisfied zones (within tolerance) rest at idle baseline.
- State 2: HEATING_CALL — same proportional model, with `high_internal_heat_load` zones inverted per the behavioral rule above.
- State 3: FAN_ONLY (Recirculation) — vents move to per-zone `idle_baseline_position`, not a blanket 100% open (see behavioral rules above).
- State 4: IDLE — same per-zone `idle_baseline_position` behavior.

### Safety & Equipment Safeguards

- Domain Research Directive: research HVAC static pressure rules, maximum allowable duct closure ratios, and equipment protection limits across single-stage, two-stage, and variable-speed systems before finalizing pressure safeguard thresholds. This is a blocking research step, same treatment as Phase 0 — research first, then confirm whether the ranges below are appropriate for this specific equipment (Bosch IDS variable-speed, bridged Y) before they're locked in as the enforced safeguard limits; don't implement against them as placeholders and revisit later. Confirmed separately (see Ecobee ↔ Bosch IDS Interface under Scheduling Engine & Data Model): for this installation, Y1/Y2 are bridged to a single Y signal — Ecobee only controls call start/stop timing, not staging or intensity. The air handler/condenser negotiate modulation autonomously; exactly which inputs that negotiation uses is proprietary and still worth investigating via Bosch's own IDS documentation, though it doesn't change this app's design conclusion (push an accurate setpoint, never a padded one).
- Topology-Aware Pressure Safeguard: CFM-weighted aggregate calculation where per-zone `duct_cfm_rating` is set; falls back to equal-weighting (simple open/closed ratio) for zones left at default. Mixed setups — some zones with real CFM data, others on default — are expected and should degrade gracefully rather than requiring all-or-nothing configuration. `manual_fixed_vent` zones count toward total system open-area/CFM using their `assumed_fixed_position` — they can't be adjusted, but they still consume or contribute to the system's closure budget, so ignoring them would make the safeguard's math wrong (e.g., a manual vent left mostly closed eats into how much the smart vents are actually allowed to close). Applies during FAN_ONLY and IDLE as well: if configured `idle_baseline_position` values across zones would collectively violate the topology's minimum open-area floor, clamp toward the floor rather than trusting the raw configured values blindly. Thresholds before writing commands:
   - Variable/Inverter Mode: up to 75%–80% aggregate closure allowed.
   - Two-Stage Mode: cap closure at 50%–60% during high-stage calls.
   - Single-Stage Mode: strict maximum 33% closure (67% minimum open area across system).
- Step-Delta Suppressor: dispatch commands only if `|target_position − reported_position| ≥ min_step_delta` (e.g., ≥15%) to reduce gear wear and preserve battery life. This governs dispatch efficiency only — see Modulation Steps & Ramp Rate Limiting (Proportional Vent Position Control, above) for how quickly the target itself is allowed to move; the two work together, not as substitutes for each other.
- Hardware Reconciliation: update `target_position` optimistically, then reconcile against `reported_position` at T+120s.
   - On reconciliation failure: retry the command a limited number of times (e.g., 3 attempts with backoff). If still unreconciled, mark the vent degraded, exclude it from all pressure-safeguard aggregate math, and surface an alert in the UI.
- Stale Sensor Reading Safeguard: the mirror image of Hardware Reconciliation, but for sensor input rather than vent output. This surfaced as a real, observed problem during review, not a hypothetical: a room's Flair-reported temperature stayed wrong (73°F vs. the Ecobee app's 71°F for the same single sensor, no separate puck involved) for far longer than any reasonable sensor reporting interval — well past 10 minutes — pointing to Flair's sync from Ecobee getting stuck for that room rather than ordinary reporting lag. Track each zone's last-changed timestamp for its Flair-reported temperature (once Phase 0 confirms it's available — see the sensor discovery item above); if a zone's reading hasn't changed in longer than a configurable staleness threshold (starting default: 15 minutes, tunable in System Parameter Configuration) while the zone is not already classified satisfied, treat that zone's telemetry as stale rather than trusting it indefinitely:
   - Exclude the zone from active demand-driven proportional control and fall back it to `idle_baseline_position` — continuing to chase a deviation computed from data that might be arbitrarily wrong is worse than doing nothing, especially since the observed failure mode is exactly "vent stays wide open long after the room is actually comfortable."
   - Log at warn level and surface a "stale reading" indicator on that zone in the UI, distinct from the degraded-vent indicator (this is a data problem, not a hardware/actuation problem, and conflating the two in the UI would send the user troubleshooting the wrong thing).
   - Once the reading resumes changing, resume normal control for that zone — no manual reset required, but the stale period itself is retained in the log/timeline for later diagnosis.
   - If Phase 0 confirms Flair offers a way to actively request a fresh read (see discovery item above), attempt that as a corrective action once a zone crosses the staleness threshold, rather than only alerting and passively waiting for Flair's own sync to recover.
- Proactive staleness monitoring, not just the reactive cutoff above: track each zone's time-since-last-change continuously, not only when checking it against the threshold, and feed it to the Grafana dashboard as a leading indicator (see Logging & Observability) — so a reading drifting toward staleness is visible before it crosses the hard threshold and forces a fallback, rather than the first sign of trouble being the alert itself.
- Equipment Fault Emergency Fail-Safe: on detection of an Ecobee equipment fault signal (e.g., high static pressure, compressor lockout) via Flair, immediately override the state machine and force all vents to 100% open, and surface a prominent UI alert. This takes priority over all other logic, including active manual overrides and any configured `max_vent_position` restriction (Zone Configuration Model) — equipment protection overrides a comfort/airflow-distribution preference.
- Startup/restart reconciliation: on service start (NAS reboot, container restart, deploy), reconcile actual Flair-reported vent positions before resuming normal control-tick behavior — don't assume the world is where it left off. Treat this the same as the T+120s reconciliation check above, just triggered by startup instead of a command.
- Config-time validation: unsafe or inconsistent values should be rejected at save time in the UI/API layer, not only caught by runtime clamping — runtime clamping is the last line of defense, not the only one. This includes: a comfort tolerance far outside a sane range, a pressure cap that would violate the topology's hard floor, a negative or absurd CFM rating, an implausibly large `sensor_calibration_offset_f` (almost certainly a mistake rather than genuine drift), `min_vent_position > max_vent_position`, and an `idle_baseline_position` that falls outside a zone's own configured `min_vent_position`/`max_vent_position` range — reject with a clear message rather than silently clamping it into range, since a silently-adjusted idle baseline is exactly the kind of surprising behavior that's hard to debug later.

### Scheduling Engine & Data Model

#### Data Structures & Event Mapping

- Schedule Object Schema (logical shape shown here; see Data Modeling Conventions above for which of these are dedicated columns vs. JSONB — `id`/`name` are columns, `default_inactive` and `events` are JSONB):
   - `id`: UUID.
   - `name`: display string.
   - `default_inactive`: boolean — whether unassigned time windows hold fallback limits or turn rooms inactive.
   - `events`: array of:
      - `start_time` / `end_time` (24hr, e.g. `20:30`–`07:00`). Windows crossing midnight are handled via explicit wraparound logic, not treated as invalid ranges.
      - `days_of_week`: stored as a Postgres smallint bitmask (single canonical representation, not array-or-bitmask).
      - `mode`: `Active` | `Inactive`.
      - `cool_setpoint` / `heat_setpoint`: °F. One value pair per event, applied uniformly to every zone in `assigned_zone_ids` — matches Flair's existing app behavior (confirmed via screenshots). Different setpoints for different zones at the same time are achieved by creating separate events/schedules per zone or zone-group, not by a per-zone setpoint map within one event.
      - `zone_priority_order`: optional ordered array of zone IDs, potentially spanning multiple air handlers (see Proportional Vent Position Control & Priority-Based Contention Resolution, and Multi-Air-Handler Architecture). Active only during this event's window; zones not listed fall back to the global default order. Ranking is evaluated per air handler — the top-ranked zone within each air handler's own subset doubles as that air handler's default driving zone (see Driving Setpoint Selection) unless overridden via `driving_zone_overrides`.
      - `driving_zone_overrides`: optional map of `air_handler_id → zone_id`. Overrides which zone's setpoint gets pushed to that air handler's Ecobee as its call target for this event, when it shouldn't just be the top-ranked zone within that air handler in `zone_priority_order`. Per-air-handler-keyed, same convention as other override fields (e.g. `comfort_tolerance_overrides`). See Driving Setpoint Selection.
      - `comfort_tolerance_overrides`: optional map of `zone_id → tolerance_f`, active only during this event's window. Zones not listed fall back to their own `comfort_tolerance_f` (or none, if unset). Always a per-zone map.
      - `assigned_zone_ids`: array of zone identifiers — covers all zone types (`flair_smart_vent`, `manual_fixed_vent`, `no_vent`), not just Flair-imported rooms, so every zone in the house is schedulable.
- Overlap tiebreak: if two events across schedules apply to the same zone at the same time, the event with the more specific `days_of_week` scope (fewer days) wins; if still tied, the more recently edited event wins.

### Manual Overrides

- User-selectable hold duration per override: 2hr / 4hr / until next scheduled event / permanent. Not a fixed global default — expose the choice at override time.
- Concurrent conflicting overrides (e.g., two household members adjusting the same zone from different devices around the same time): last-write-wins, logged clearly (who/when/what) so it's visible after the fact rather than silently discarded.

### Target Resolution Order

For every dynamic control tick:

1. Manual Room Overrides — active until their selected hold expires. Takes precedence even while Away Mode is active — an explicit manual adjustment for a specific zone always wins.
2. Away Mode — if active (see below), applies a global away setpoint and wide tolerance across all zones not covered by a manual override, superseding the normal schedule.
3. Active Schedule Event — resolves `cool_setpoint`/`heat_setpoint`, `zone_priority_order`, and `comfort_tolerance_overrides` for matching zones, when Away Mode is not active.
4. Fallback Baseline — global fallback targets if no event matches and `default_inactive` is false.

### Driving Setpoint Selection (What Actually Gets Sent to Ecobee)

Per-zone `cool_setpoint`/`heat_setpoint` values drive vent proportioning (see Proportional Vent Position Control) — they do not, by themselves, tell Ecobee when to call for heat/cool. Each air handler's Ecobee thermostat makes exactly one call decision for that air handler, comparing one pushed target against one sensor (or sensor group). Something has to be that one target — per air handler, since each of the 3 air handlers has its own independent Ecobee (see Multi-Air-Handler Architecture).

- Driving zone (per air handler) = the top-ranked zone within that air handler's subset of the currently-active `zone_priority_order` (schedule override if active, else global default) — reuses the existing priority list rather than introducing a new config surface. That zone's resolved `cool_setpoint`/`heat_setpoint` is what this microservice writes to Flair's `structures.set-point-temperature-c` for that air handler's structure (per Integration Mode's "Flair App" authoritative setpoint control), each time it changes.
- Optional explicit override: a schedule event may designate a different zone as that air handler's driving zone via `driving_zone_overrides[air_handler_id]` if the top-of-priority zone within that air handler shouldn't also be the one driving equipment runtime — not expected to be common, but the priority list's purpose (vent allocation under contention) and the driving-zone's purpose (equipment call timing) are conceptually distinct, so forcing them to always be identical would be a coincidence, not a guarantee.
- What this means physically: other zones on the same air handler don't get an independent call — they get a proportional share of whatever conditioned air flows while that air handler's compressor runs to satisfy its driving zone. A looser zone (e.g., 72–74°F tolerance) typically reaches comfort during that same run, since it's an easier target than the driving zone's; if it hasn't by the time the driving zone is satisfied and the call ends, it simply waits for the next call cycle rather than being independently conditioned. This is entirely per-air-handler — zones on different air handlers are never in contention with each other, since each air handler runs its own independent call.
- Critical dependency — must be verified in Phase 0, for each air handler independently: this only works correctly if an air handler's Ecobee's own active "comfort setting" sensor-group selection actually matches that air handler's driving zone (e.g., an Ecobee "Night" comfort setting needs bedroom SmartSensors selected, not some unrelated sensor). Sensor-group selection is Ecobee-native configuration — same boundary as vent/sensor-to-room pairing in Configuration Responsibility above — this app doesn't control it, but it needs to be kept in sync manually, per air handler. If an air handler's Ecobee is comparing against the wrong sensor(s), it'll stop calling based on a zone this app isn't even treating as that air handler's driving one, and the whole scheme silently breaks for that air handler.

### Ecobee ↔ Bosch IDS Interface: Confirmed Topology, and the Generalized Setpoint-Push Mechanism

Confirmed for this specific system: Y1 and Y2 are bridged at the air handler — only a single Y signal reaches it, meaning Ecobee cannot send a two-stage signal at all here, regardless of what general research on Y1/Y2-staged variable-speed installs might suggest. Per the installer, this is Bosch's own recommended configuration for pairing IDS with a third-party thermostat — not an installer shortcut or wiring issue to revisit. The air handler and condenser negotiate modulation directly with each other, independent of Ecobee — almost certainly using their own inputs (refrigerant pressures, discharge/suction temps, elapsed call duration, possibly the air handler's own onboard return-air sensor), not anything Ecobee computes. Ecobee's role here reduces to exactly one lever: when the call starts and when it stops. It has no channel to communicate urgency or intensity to the equipment at all — so a pushed value can only affect call duration, never modulation intensity, for this system.

What's still unverified and equipment-specific: exactly what inputs the Bosch air handler/condenser link actually uses for its autonomous modulation decision (time-based ramp schedule, its own return-air sensor, a refrigerant-side target) isn't something generic Ecobee-compatibility research can answer — it's proprietary to Bosch's IDS communicating protocol. Worth digging into Bosch's own IDS technical/service documentation for, as part of the existing Domain Research Directive, though it doesn't change the design conclusion below, since this app never has a channel to influence compressor modulation intensity regardless of the specifics.

Design conclusion — must generalize across Single-Stage, Two-Stage, and Variable-Speed, since the system config is meant to support all three: the mechanism has to be split into two distinct pieces, not one blind rule, because a naive "push a fixed aggressive value for the whole call, correct only at the end" approach is not safe for genuinely-staged systems (distinct, non-bridged Y1/Y2) — Ecobee's own stage-2 escalation logic on those systems typically triggers off a large, sustained gap, so an artificially padded value held for the whole call would risk exactly the kind of unnecessary escalation this design is meant to avoid. Splitting it removes that exposure:

1. Throughout the call — accurate, continuous tracking, never padded. The pushed value tracks the actual driving-zone need as closely as possible at all times:
   - Preferred, if available (Phase 0-dependent): automated Ecobee comfort-setting sensor-group matching — switch the active sensor group to the current driving zone, so Ecobee compares against real data directly. Nice-to-have, not load-bearing — the mechanism below works correctly with or without it.
   - Otherwise: continuous measured-offset correction — compute the live delta between the main thermostat's reading and the driving zone's actual reading (from existing per-zone telemetry) each tick, and push `driving_zone_setpoint + measured_offset`, lightly smoothed to avoid feeding noise into the pushed value. The goal throughout is accuracy, never urgency — on a staged system, this means Ecobee only ever sees a real, shrinking gap, so it only escalates when the room genuinely warrants it. On a bridged/communicating system like this one, it just keeps call duration honest.
2. At the moment this app's own telemetry confirms all currently-relevant zones are satisfied — a prompt termination override. Rather than waiting for Ecobee's own (possibly laggy, possibly differently-located) sensor to naturally converge on the accurately-tracked target, snap the pushed value to match (or just past, in the satisfied direction) Ecobee's current comparison reading the instant this app knows the driving zone is done. This piece only ever nudges toward stopping — it can't manufacture urgency or trigger escalation on any system type, since it's strictly a call-termination signal, not a demand signal. It's a pure improvement: faster, more precise call-ending, with no exposure on staged systems.

Both pieces matter for genuine cross-system genericness: piece 1 keeps the signal honest while a call is active (safe for staged systems), piece 2 makes termination prompt and precise regardless of Ecobee's own sensor placement or convergence speed (valuable for every system type, including this one).

### Away Mode

- Source, per Phase 0 discovery: prefer Ecobee-sourced Home/Away state if Flair reliably surfaces it. If not available, implement a native Away toggle in this app instead — this microservice already owns scheduling and manual overrides, so a native toggle is a small addition, not a workaround.
- Behavior: reuses the existing Comfort Tolerance mechanism rather than inventing new logic — while Away, apply a configurable global away setpoint plus a wide "away tolerance" (e.g., ±5°F, configurable) across every zone, overriding per-zone/schedule tolerance for the duration. Most zones become "satisfied" almost immediately, minimizing vent churn while unoccupied.
- Dynamic Thermal Spike Detection remains active while Away (e.g., to catch an appliance malfunction), since that's a safety-relevant signal regardless of occupancy.
- Surfaced in Phase 1's global system status (Home/Away state) and configured in Phase 2's System Parameter Configuration (away setpoint, away tolerance, and the native toggle if Ecobee-sourced state isn't available).

### Control Loop Cadence

- Default 60-second control tick, with write batching/backoff to respect Flair API rate limits — balances responsiveness against the 30–90s vent actuation latency and 120s reconciliation window. This cadence governs how quickly the app reacts to whatever sensor data is currently available — it does not, by itself, determine how fresh that sensor data actually is. Real-world Ecobee/Flair sensor reporting latency (often minutes) appears to be a sensor/reporting-cadence limitation upstream of this app; shortening the tick below 60s would mostly just re-poll the same stale cached values more often at the cost of Flair API rate-limit budget, not produce fresher readings.

### Time Handling: Local Display, UTC Persistence

All times are entered and displayed in local time; all persistence uses UTC — but recurring schedule times and absolute event timestamps need different treatment to avoid a common DST bug:

- Recurring schedule event times (`start_time`/`end_time`, e.g. `20:30`–`07:00`): store as wall-clock local time (not pre-converted to a UTC offset), tagged against a single system-configured home timezone (IANA identifier, e.g. `America/Phoenix`). Compute the actual UTC instant at evaluation time using the current date + timezone rules — converting once at save time and storing a fixed UTC offset will silently produce the wrong local time across a DST transition.
- Absolute point-in-time values — manual override expiry, historical telemetry, hardware reconciliation timestamps, spike-detection events, sync timestamps — are genuine instants: store as UTC (`timestamptz` in Postgres), convert to local only at the display layer.
- Home timezone is a single system setting, not browser-detected. Schedules govern a physical space, so the app should always evaluate and display schedule times against the configured home timezone, regardless of what timezone the viewing device happens to be in (e.g., accessing the UI while traveling shouldn't reinterpret "night mode starts at 20:30" as 20:30 in some other timezone).

## UI Requirements & Functional Design Contract

### Styling & Design Framework

- Built strictly using React with Material UI (MUI). Zero external CSS — `sx` prop, `styled` utilities, and theme tokens only. `tesla-powerwall-automation` already has an established theme layer/token set — reuse it directly rather than building fresh.
- Theme mode: support system auto-detect (`prefers-color-scheme`) and a manual light/dark toggle that overrides it, persisted per user. This is the one gap in the reference app's theme provider — it currently only auto-detects and has no manual override — so this project needs to add that toggle itself, and it's worth backporting the fix to the reference app's shared theme provider.
- Diagnostic Mode: a second app-wide toggle, same persistence pattern as theme mode (per-user, overrides a default of off), that extends the existing screens in place with additional under-the-hood fields rather than sending the user to a separate debug screen to piece things together. The point is reducing "jump back and forth" during troubleshooting, not adding a whole parallel UI. When on, it reveals: each zone's raw (uncalibrated) Flair-reported temperature alongside the calibrated value used for control (only meaningfully different when `sensor_calibration_offset_f` is set, but shown whenever Diagnostic Mode is on rather than only when the offset is nonzero, since the point is a consistent, predictable place to look); per-zone time-since-last-sensor-update (the same leading indicator that's on the Grafana dashboard, surfaced here too for in-the-moment troubleshooting without switching to Grafana); sensor disagreement values where that diagnostic applies; each vent's configured `min_vent_position`/`max_vent_position` range shown right alongside its current opening percentage, so a vent parked well short of 100% reads as intentionally capped rather than possibly stuck; and hardware reconciliation detail (retry attempts so far, degraded-vent history) beyond the plain Target vs. Reported shown by default. New diagnostic fields added later should default to living behind this toggle rather than each getting its own one-off decision about whether to clutter the default view.
- Mobile responsiveness: already an established convention in `tesla-powerwall-automation` — follow its existing responsive breakpoints and layout patterns rather than reinventing. One implementation-specific callout: the drag-and-drop zone priority lists (see below) must support touch-based reordering (drag handles, long-press-to-drag), with an accessible up/down-arrow-button fallback for small screens or non-pointer input.

Environment access for implementation: the centralized infrastructure already exists (Postgres, Redis, Loki, Grafana, Caddy, Docker registry, GitHub Actions runner) since `tesla-powerwall-automation` is already deployed on it — nothing new to provision. Claude Code can reach the NAS via SSH and GitHub via the `gh` CLI, but real access is gated by user interaction rather than being fully autonomous — expect to be pulled in for approval/execution steps rather than this running fully unattended end-to-end. The Grafana dashboard is authored as code (JSON model / provisioning file) and deployed manually by the user by default; it's worth checking whether Grafana's dashboards HTTP API or file-based provisioning can be used to push it automatically instead, though manual import is perfectly fine if that turns out not to be worth the trouble.

Not required for initial implementation — noted here so it isn't lost, and so nothing in the MVP data model actively forecloses it later.

- Automatic Vent Calibration Recommendation: two complementary modes:
   - Passive observation: observe each zone's temperature response rate (°F/min) during ordinary heating/cooling cycles at known vent positions, across enough cycles to be statistically meaningful. Low-friction, but slower and noisier — confounded by whatever else is happening in other zones at the same time.
   - Active/controlled calibration mode: user-initiated, bounded-duration test (length configurable — an hour or whatever proves sufficient in practice) that isolates one zone at a time. Holds all other zones at a fixed known baseline, sets the target zone's vent to a known test position, and measures its temperature response while an active heating/cooling call is genuinely running (if no call is active when the test starts, defer or warn rather than recording a meaningless flat-line result). Can be run per-zone on demand, or as a sequential "Calibrate All Zones" routine that steps through each zone one at a time. Must still respect the Topology-Aware Pressure Safeguard's closure limits during the test — calibration doesn't get an exemption from equipment protection. Normal automatic control resumes once the test completes.
   - Both modes feed the same output: a recommended `idle_baseline_position` and/or refined `duct_cfm_rating` per zone, surfaced for the user to review/approve — never auto-applied silently, given this drives physical equipment behavior.
   - Naturally builds on the Phase 3 historical telemetry once that data exists — this is a downstream consumer of that data, not a new data source.

## Testing & Safety Validation (Required Deliverable, Built From the Start)

Vitest is the required framework for both unit and functional tests. Tests are written alongside the logic they cover, in the same PR/commit as the feature — not as a follow-up pass, and not skipped to hit a phase deadline. Wire the test run into the existing GitHub Actions CI pipeline as a gate before deploy.

Mocking strategy — mock liberally where it keeps tests fast and deterministic, especially anything crossing a network or wall-clock boundary:

- Flair API calls: mocked in all functional tests via a mock HTTP layer (e.g., `msw` or a hand-rolled mock client) — not just happy-path responses, but simulated error responses, rate-limiting, degraded/unreconciled vent positions, and equipment fault signals, since those are exactly the paths hardest to exercise against the real API on demand.
- System clock: any test involving time-based logic — DST transitions, spike detection decay/hysteresis, comfort tolerance timing, schedule evaluation, manual override expiry — uses Vitest's fake timers rather than real sleeps or waiting for actual wall-clock time to pass.
- Redis/Postgres: pure unit tests shouldn't need either at all (test the logic functions directly with plain inputs/outputs). Functional tests can use a disposable test instance/container where the persistence or rolling-buffer behavior itself is what's under test — no need to mock those when the point of the test is to verify real read/write behavior.

Unit tests — pure logic, fast, no I/O, no mocked network calls:

- Proportional position calculation: correct linear scaling between idle baseline and max position across the configured band width, correct clamping beyond the band, correct modifier application (occupancy/spike/thermal flags), in isolation from any live data source.
- Sensor calibration offset: raw reading plus `sensor_calibration_offset_f` produces the correct calibrated value, and every downstream consumer (deviation calculation, tolerance classification, spike detection, driving-zone offset correction) uses the calibrated value, not the raw one; a zero/unset offset is a no-op.
- Per-vent position range (`min_vent_position`/`max_vent_position`): desired and ramped positions are clamped within a configured range at every stage (Step 1 through Step 3); `idle_baseline_position` outside the configured range is rejected at config-validation time rather than silently clamped; Emergency Fail-Safe correctly bypasses the range and forces 100% regardless.
- Modulation step quantization and ramp rate limiting: a large sudden jump in desired position (e.g., spike detection firing) ramps toward the target over multiple ticks rather than commanding it in one step; Emergency Fail-Safe correctly bypasses ramping.
- Contention resolution: tolerance exclusion → schedule/global order resolution → spike/occupancy bucket partitioning, invoked only when aggregate desired capacity exceeds the pressure cap.
- Pressure safeguard math across all three HVAC topology modes (Single/Two-Stage/Variable), including CFM-weighted vs. equal-weighting fallback and pressure-floor clamping.
- Comfort tolerance resolution (schedule override → zone default → none) and satisfied/demanding classification.
- Dynamic thermal spike detection: threshold triggering on rate-of-rise, decay/hysteresis behavior. **Include a case with irregular/sparse reading timestamps (simulating multi-minute Flair/Ecobee reporting latency) to confirm rate-of-rise is computed against actual reading spacing, not assumed fixed tick intervals.**
- Target Resolution Order (manual override → schedule event → fallback baseline), including overnight-window wraparound and overlap tiebreak logic.
- Recurring schedule evaluation across a DST transition (spring-forward and fall-back) — resolves to the correct wall-clock local time, not a stale fixed UTC offset.

Functional/integration tests — control loop behavior end-to-end, with the Flair API mocked:

- A full control tick with no contention: each demanding zone receives its own independently-computed proportional position, unaffected by priority order.
- A full control tick under genuine contention: more aggregate desired capacity than the pressure cap allows, asserting reductions apply lowest-priority-first and preserve higher-priority zones' desired positions as fully as possible.
- FAN_ONLY/IDLE per-zone baseline positioning, including pressure-floor clamping when configured baselines would collectively over-close the system.
- Mixed vent hardware types: `manual_fixed_vent` zones excluded from allocation but included in pressure-safeguard math via their assumed fixed position; `no_vent`/sensor-only zones contribute telemetry without being targeted for control.
- Hardware reconciliation: retry → degrade → exclusion from pressure math, and emergency fail-safe triggering on a simulated equipment fault signal.
- Flair sync reconciliation: new-room match-to-existing-zone flow, sensor add/remove auto-update, vent/sensor removal graceful degradation.
- Away Mode: correct target/tolerance override applied across zones, manual overrides still taking precedence, and correct fallback behavior between Ecobee-sourced and native toggle sources.
- Driving Setpoint Selection: correct zone resolved as driving (top of priority order, or explicit override) and correct value written to Flair's structure setpoint; verify it changes appropriately as schedule events transition.
- Offset correction (if sensor-group switching isn't available): pushed setpoint reflects the actual measured delta between main thermostat and driving zone, never an arbitrarily padded value that would extend call runtime past what the driving zone needs; smoothing correctly dampens noisy offset swings rather than feeding raw noise into the pushed value.
- Prompt termination override: once all currently-relevant zones are confirmed satisfied, the pushed value snaps to force call termination rather than waiting on natural convergence.
- Cross-system-type safety: simulate a Two-Stage configuration specifically and verify the accurate-tracking mechanism never holds an artificially padded gap long enough to trigger unnecessary stage-2 escalation — this is the scenario that would fail if the two pieces of the mechanism were collapsed into one "push aggressive, correct at the end" rule.
- Startup reconciliation: service restart correctly reconciles actual vent positions before resuming normal ticking, rather than trusting stale in-memory state.
- Safety-relevant events (emergency fail-safe, degraded vent, pressure clamping) are logged at warn/error, visible/queryable in Grafana, and trigger the email alert path with secrets correctly redacted from the log payload.
